# qare init: onboard a repository in one command

Issue #146

## Scope

In:

- `qare init [path]`: runs the readiness inventory, then writes a starting
  `.qa/` (config.yml, QA.md, and for a booted profile fixtures/ and stubs/)
  and the caller workflow `.github/workflows/qare.yml` for the reusable
  pipeline (#145).
- A repository with a compose file gets an `app` profile: the compose file,
  the service that looks like the application, a health URL read from its
  healthcheck and published port, one stub per outbound origin, and any suite
  init recognises (Cucumber, Playwright, RSpec system tests).
- A repository with no compose file gets a `target` profile, from
  `--target <url>`.
- Never overwrite: an existing `.qa/` or caller workflow is left alone, and
  init prints what it would have written.
- The end of the output lists every readiness gap as a next step, and names a
  stub issue for every stub gap. `--file-issues <owner/name>` files them
  through the same draft and dedup marker the pipeline uses (#31).
- Readiness learns what init leaves open, so `qare readiness` names exactly
  what is missing: a placeholder init wrote and nobody filled in, a compose
  file or service the profile names that does not exist, and a stub whose
  compose service nothing defines. Loopback hosts and the compose file's own
  service names stop counting as outbound origins.
- A test that holds the generated caller to `pipeline.yml`'s inputs, to the
  released version, and to the caller `docs/pipeline.md` shows.

Out:

- `.github/workflows/*` and the images: #209 is changing them in parallel.
- Writing the stub services themselves: what a stub must answer is the
  repository's knowledge. Each becomes a stub issue.
- Guessing a target URL: with no compose file and no `--target`, init stops
  and names the flag, and writes nothing.
- Monorepo layouts with several profiles (#55): init writes one root profile.

## Assumptions

- The generated workflow pins `VERSION` from `@qare/core`, which
  `scripts/sync-version.mjs` already stamps from package.json, so the pin
  cannot drift from the release and needs no new stamp.
- Placeholders are `TODO(qare init): <what to do>` lines. Readiness reports
  each one in `.qa/QA.md` and `.qa/config.yml` as a gap, so init's own list
  of next steps is the readiness report's and nothing else.
- The application service is `--service <name>` when given; otherwise the
  first service with `build:`, then the first that publishes a port, then the
  first by name.
- A stub is named for its host (`api.stripe.com` becomes `api-stripe-com`,
  provided by `api-stripe-com-stub`), so two hosts never share a name.
- The model defaults to the one `docs/pipeline.md` shows, with
  `--model <name>` to change it; the key is the `OPENAI_API_KEY` secret.
- The push trigger that re-queues refused pull requests is written only for
  a booted profile, for the branch `origin/HEAD` names (`main` when unknown).
- Filing issues is opt-in: the scan reads every URL in the tree, so a person
  prunes the stub list before issues are filed for it. `@qare/cli` takes
  `@qare/action` as a dependency for its GitHub client and stub issue poster.
