# A main lane: the pipeline runs the ledger's active criteria on the default branch and hands the judged result to main-findings

Issue #294

## Scope

In: three jobs in `.github/workflows/pipeline.yml` (`main_collect`,
`main_execute`, `main_judge`) behind the input `main-lane`, a dry run unless
`main-lane-dry-run` is the exact word `false`; `qare ledger plan`; `qare judge
--no-diff`; the dry run of `qare-action main-findings` printing the issues it
would open; one fix to how a run on main is classified; the docs.

Out, and why:

- Writing to the ledger from the lane. Criteria change only through review
  (CONSTITUTION.md rule 5), and a `verify` record is a ledger change.
- Planning with the model on main. See the first assumption.
- Screenshots on `qa-assets`, client artefacts and run metrics on main. Each
  needs a permission or an input the lane does not otherwise need, and none
  is needed to file a finding.
- Turning the lane on in qare's own repository, which has no ledger.

## Assumptions

- **Recorded checks, not a re-plan.** The ledger records, for each
  criterion, the checks it is verified by. A `suite:<name>` reference names a
  suite in the profile, whose command the runner can execute; `qare run
  --criteria` already builds a plan from exactly that. So the lane's plan is
  read out of the ledger by code and no model plans on main. This is cheaper
  (no planner turn on a schedule), it is the same every run (two runs of one
  revision check the same things), and it keeps a model out of the decision
  of what a run on main checks. The cost: a criterion whose ledger checks
  name no suite cannot be run. It is reported unverified with that reason
  and files nothing.
- **The verifier still runs.** `main_judge` is `judge` with no pull request:
  the verifier reads the evidence of each proven criterion and may overturn
  it, so a suite that exited 0 without showing its criterion does not close
  an open issue. It is told there is no change under review, in the words
  `qare check` and `qare ingest` already use.
- **In `pipeline.yml`, not a sibling workflow.** A caller pins one release
  in one `uses:` line, grants one permission ceiling and passes its model
  key and identity once. A sibling workflow would be a second pin to keep in
  step and a second copy of the secret map. The price is a longer file; the
  shared steps are the same text, and a test holds them equal.
- **New jobs, not branches inside the old ones.** `collect`, `plan`,
  `execute` and `judge` are pull request shaped throughout (base and head,
  the diff, the comment). Giving each a second mode would put the pull
  request lane, which gates every change here, at risk for a lane that is
  off by default.
- **Job ids use an underscore.** `packages/cli/test/workflow.test.ts` finds
  the end of a job section with `/^  \w+:$/`, which a hyphen would not match.
- **Only `active` criteria run.** A `proposed` criterion has not been proven
  by anything, so its failure is not a finding on main.
- **The default branch alone, on an allowlist of events.** `push`,
  `schedule` and `workflow_dispatch`, and only when the ref is the default
  branch. A pull request, a comment, a tag or another branch starts nothing.
- **Dry run by default, and fail safe.** Anything but the exact word `false`
  is a dry run, so a typo cannot open issues or mention people.
