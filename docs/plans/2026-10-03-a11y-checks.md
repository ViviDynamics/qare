# Accessibility checks: new violations fail, old ones are reported

Issue #149

## The gap

A flow can prove every stated criterion on a screen nobody can use with a
keyboard or a screen reader. Accessibility rules are objective, so code can
check them and put the answer in the verdict (rule 3). Today the only
accessibility signal is the #82 finding in a flow's assertion snapshot, which
is logged and decides nothing.

## Scope

In:
- An `a11y` check kind in the plan and the job. It names a page (`url`) or
  drives to one with the flow vocabulary (`actions`), and audits the pages it
  visits with axe-core, injected through the browser driver.
- The audit rides the flow session: the page is audited in the state the flow
  left it, at each of the profile's widths and themes (`visual.widths`,
  `visual.themes`, or the check's own), by resizing the viewport and
  emulating the colour scheme in place. Nothing is driven twice.
- A profile `a11y` section: `standard` (the rule set, `wcag22aa` by default),
  `fail` (the impacts that fail, `serious` and `critical` by default),
  `accept` (known violations, each with a `reason`), and `standing`, which
  audits every action flow of the run without a planned check.
- New versus existing, on the #147 mechanism exactly as visual checks use it
  (#143): the base side audits and saves `a11y.json` under `base/`; the head
  side reads it and fails only on violations the base did not have. One-sided
  runs have nothing to excuse a violation with, so each one fails.
- Evidence: `a11y.json` per check, naming each violation with its rule,
  impact, the element's role, accessible name and path from the normalised
  snapshot (#82), its selector, its status (`new`, `existing`, `accepted`,
  `reported`, `uncompared`) and the screenshot of the page it was found on.
  The record text is swept by the run's redaction rules; screenshots are
  masked at capture and withheld while a one-time code is on the page.
- The criterion result carries the counts, and the comment lists them, so
  existing violations are reported where the verdict is read.
- The planner is told the kind exists, and to mark it `inferred` when the
  criterion did not ask for it.
- SPEC, schemas, writing-criteria.

Out:
- Drivers other than the browser. A driver with no audit seam leaves the
  check `unverified`, naming that.
- Suite flows (`flow` with `suite`): the suite runs its own browser, which
  qare cannot audit. `standing` covers action flows only.
- axe's `incomplete` results (needs human review). They are counted in the
  record and decide nothing.
- Content inside frames. Only the page's own document is audited.
- `qare doctor` naming the browser as required for a profile whose only
  browser need is its `a11y` section.
- UX findings from a model (the other half of epic #148).
- Workflow files. Nothing in the pipeline changes.

## Assumptions

- Outcome rules, all in code (rule 3):
  - An audit that cannot be made (no audit seam, axe-core missing, the page
    threw) is `unverified`, naming why. Fail closed (rule 6).
  - The flow part decides first: a failed assert is `failed`, an action that
    could not run is `unverified`, as for a flow. The audits made up to that
    point are still written.
  - Base side: the audit is recorded and decides nothing there.
  - One side (a target, or no base asked): a violation at a failing impact
    that is not accepted fails the check.
  - Two sides: a head with no failing violation passes without reading the
    base. Otherwise each head violation is matched against the base audit at
    the same audit point, width and theme. Matched is `existing` and does not
    fail. Unmatched is `new` and fails, naming rule and element. When the
    base has no audit to match against (it did not boot, the limits left the
    criterion out, its flow stopped earlier) the violation is `uncompared`
    and the check is `unverified`, never failed and never passed; that
    outcome is not cached.
- Matching: first on the exact identity (rule, snapshot path, selector), then
  on the path with occurrence indexes dropped, each base violation matching
  once. Adding one unnamed button beside an old one reports one new
  violation, not two.
- Audit points: after each `open`, after each `waitFor`, `assertText` and
  `assertElement` that held, and at the end of a flow that passed, skipping a
  point when nothing acted on the page since the last one. These are the
  states the plan itself declared settled.
- The rule set, impacts, accepted list and widths and themes in force at the
  base are the head profile's, as masks are (#143): turning the check on in
  a pull request compares both sides under the same rules, so old debt is
  `existing` from the first run.
- With no width configured anywhere the audit runs once at the viewport the
  flow ran in. No theme means `light`.
- `accept` entries match on `rule`, and optionally `page` (the URL path) and
  `element` (the snapshot path or the selector). Accepted violations are
  listed with their reason and never fail. The configuration in force is
  written into the record, so a pull request that adds an entry shows it.
- axe-core is an optional dependency beside playwright-core (MPL-2.0, used
  unmodified). Its `html` snippets are not recorded: the selector, role, name
  and path identify the element, and markup is where fixture data leaks.
- An `a11y` check takes `url` or `actions`, not both; neither audits the
  app's root. `url` resolves as a visual check's does.
